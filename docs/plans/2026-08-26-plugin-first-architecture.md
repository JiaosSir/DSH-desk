# 「一切皆插件」架构演进方案（桥服务化 + 原生执行器）

> 状态：**方案（未实施）**。日期：2026-08-26。
> 背景：参考项目调研见 [`docs/research/2026-08-26-dsh-desktop-reference.md`](../research/2026-08-26-dsh-desktop-reference.md)。
> 现状：Tauri 壳 + sidecar 子进程 + 桥插件（`window.__DSH_DESK__` IPC 桥）。

## 一、背景与动机

「一切皆插件」是 DSH 的核心理念（整个 harness 就是 Cordis 插件树）。参考项目 dsh-desktop 把桌面壳也做成了插件（同进程 boot），获得了深度集成与正式服务契约，但牺牲了容错（Host 崩 = 整个应用崩）。

**核心判断**：「能力插件化」与「进程同体化」是两件事，可以拆开。我们采用：

> **能力以插件形态活在 harness 树里（sidecar 进程内），原生执行器留在 Tauri 壳里（进程外），两者用受控 HTTP 通道连接。**

这样「一切皆插件」理念成立（桌面能力 = 桥插件 = 插件树成员），同时保留我们的进程隔离、轻量、分发优势。

## 二、决策记录

| # | 决策 | 理由 |
|---|---|---|
| D1 | 桥插件升级为 desktop-shell 角色（宿主半部承担全部桌面能力编排） | 桌面能力以插件形态存在，第三方可组合；不新建插件行，复用现有桥 |
| D2 | 壳 = 原生执行器 + 监督器；新增**命令端口**（Rust HTTP server，随机端口 + token） | 宿主半部需要原生能力时经 HTTP 调用；与 harness 内部风格一致、可 curl 调试、天然支持响应 |
| D3 | 页面通道统一走**同源 HTTP 路由** `/api/desktop/*`（loopback + 同源校验）；`__DSH_DESK__` 双向事件通道降级为壳私有增强 | 参考项目验证过的正门模式；私有双向通道保留低延迟场景（审批实时推送） |
| D4 | 命令通道 token 经启动 env 注入（`DSH_DESK_CMD_URL` + `DSH_DESK_CMD_TOKEN`） | 与现有 PATH 注入同一机制；无壳时（纯浏览器）宿主半部找不到 env → 全部能力优雅退化 |
| D5 | 公开服务契约：`desktopState` / `desktopCommands`（d.ts 随桥发布），供第三方插件注入 | 正门契约：声明清晰、实现私有、无 IPC 后门 |
| D6 | 不引入补丁机制（暂缓）：上游 bug 先绕行/上报；仅在「bug 已确认 + 影响桌面体验」时按需引入，配双断言测试 | 零补丁是现状优势；补丁是例外工具不是默认手段 |
| D7 | 不学多 profile / 插件市场 / 三种窗口呈现模式 | 当前产品无此需求，避免「看起来酷但不解决问题」的投入 |

## 三、目标架构

```
┌────────────────────────────────────────────────────────────────────┐
│  Tauri 壳（Rust）—— 原生执行器 + 监督器（进程 A）                     │
│                                                                      │
│  ┌────────────┐  ┌──────────────┐  ┌────────────────────────────┐  │
│  │ 监督器      │  │ 原生执行器     │  │ 命令端口（新增，Rust HTTP）   │  │
│  │ 拉起/重启   │  │ restart_host │  │ 127.0.0.1:随机端口          │  │
│  │ 端口/状态机 │  │ open_logs    │  │ 接收 sidecar 插件的命令       │  │
│  │ 版本刷新    │  │ notify       │  │ POST /cmd {token, 命令}      │  │
│  │            │  │ set_autostart│  └───────────▲────────────────┘  │
│  └────────────┘  │ get_hotkey   │              │ ① 命令通道（HTTP）  │
│                   │ quit         │              │   启动时经 env 注入  │
│                   └──────────────┘              │   DSH_DESK_CMD_URL │
│  WebView2 ← 导航到 http://127.0.0.1:<port>/     │   + TOKEN          │
└──────────────────────┬──────────────────────────┼────────────────────┘
                       │ ② 页面 → 宿主半部（同源 HTTP 路由）
                       │    /api/desktop/*  （loopback + 同源校验）
┌──────────────────────▼──────────────────────────▼────────────────────┐
│  sidecar（node bin.js --profile DSHdesk）—— harness 宿主（进程 B）    │
│                                                                      │
│  ┌─ Cordis 插件树 ────────────────────────────────────────────────┐  │
│  │  dsh-base（核心 agent/模型/工具/会话）                           │  │
│  │  dsh-web-app（Web 载体，webserver）                             │  │
│  │  @cjiaojiao/dsh-desk-bridge  —— 升级为 desktop-shell 角色        │  │
│  │   ├─ 宿主半部（Node 插件）                                      │  │
│  │   │   路由 /api/desktop/*（设置/重启/日志/状态）                  │  │
│  │   │   公开服务契约（desktopState/desktopCommands）               │  │
│  │   │   事件编排（审批镜像、宿主状态）→ ① 转发壳执行原生动作          │  │
│  │   └─ 客户端半部（浏览器）                                        │  │
│  │       设置区 UI · 特性检测 · 服务注入（走 ② 路由，不再直摸 IPC）   │  │
│  │  第三方插件（可选）：inject desktopState / desktopCommands        │  │
│  └────────────────────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────────────────────┘
```

**读图原则**：页面有事找宿主半部（②），宿主半部有原生需求找壳（①），壳不直接碰页面，页面不直接碰壳。命令单向（宿主→壳，带响应），事件单向（宿主→壳），都走 HTTP。

## 四、两条通道详解

### ① 命令通道（新增）：宿主半部 → 壳

- 壳启动 sidecar 时注入 `DSH_DESK_CMD_URL=http://127.0.0.1:<随机端口>` 与 `DSH_DESK_CMD_TOKEN=<随机>`（与现有 PATH 注入同一处）；
- 桥插件宿主半部启动时读取；需要原生能力时 `POST /cmd`；
- 壳侧命令端口（Rust 轻量 HTTP server）校验 token → 分发给原生执行器；
- 选型理由：与 harness 内部风格一致（全 HTTP）、可 curl 调试、天然支持响应、无新协议。

### ② 页面通道（改造）：页面 → 宿主半部

- 客户端半部设置区 UI 从直摸 `__DSH_DESK__` 改为 fetch 同源路由 `/api/desktop/*`（loopback + 同源校验）；
- `__DSH_DESK__` 双向事件通道保留，降级为壳私有增强（低延迟场景，不进公共契约）。

## 五、场景走查

**A. 设置页「打开日志目录」**

```
页面 → fetch /api/desktop/open-logs（同源）
     → 宿主半部 handler（校验 loopback/同源）
     → POST 壳命令端口 {cmd:"open_logs"}
     → Rust 执行器：explorer 打开日志目录 → 返回路径
     → 宿主半部 → 页面
```

**B. 宿主审批事件 → 系统通知**

```
宿主半部旁听审批事件（不变）
     → 壳命令端口 {cmd:"notify", ...}   ← 不再绕页面中转
     → Rust 执行器弹系统通知
```

**C. 第三方插件用桌面能力**

```
插件 inject ['desktopState', 'desktopCommands']（公开契约，d.ts 随桥发布）
     → ctx.desktopCommands.openLogs() → 宿主半部 → 壳
```

## 七、借鉴 / 保留 / 优化清单

### 借鉴（来自参考项目）

1. **桥服务契约化**（阶段 1，最高优先）：公开服务 + 同源路由，第三方插件可复用桌面能力；
2. **健康 checkpoint**：每次健康启动写三槽配置快照，崩溃后可显式还原（与架构哲学无关，随时可做）；
3. **启动分档 + 每档失败路由**：错误信息精确到「哪一步挂了」；
4. **轻量补丁机制**（克制）：仅在确认的上游 bug 上用，配双断言测试（补丁文件 + 安装后内容各断言 marker）；
5. **渲染健康门禁**：页面回 POST boot 报告，壳判定 healthy 才提交状态（解决 WebView 白屏无感知问题）。

### 保留（护城河，转型中不丢）

| 保留项 | 原因 |
|---|---|
| sidecar 单文件分发（tar + 首启解压 + 版本刷新） | 安装轻量、升级无感 |
| 进程隔离 + 监督器（退避重启、换端口） | 容错是桌面产品生命线；宿主崩 ≠ 应用崩 |
| 轻量壳（Tauri/WebView2） | 体积、内存、启动速度 |
| 壳不读凭证、WebView 导航白名单 | 安全边界 |
| 桥插件双环境退化（纯浏览器自动 no-op） | 一个包两端用 |
| profile 只登记不安装（2026-08-26 治本） | 与参考项目共识一致 |
| Rust 侧原生能力（快捷键、开机自启、托盘） | 已稳定，保持「壳 = 原生执行器」定位 |

### 优化（超越参考项目）

1. **故障隔离**：他们同进程（Host 崩 = 应用崩，靠恢复窗口兜底）；我们插件化后仍是双进程，sidecar 崩了壳直接重启；
2. **升级成本更低**：他们换 commit + 重写 17 补丁；我们 `sidecar:assemble` 重打包；
3. **补丁清单更短**：Electron 特有补丁（RunAsNode 清理、windowsHide、open）我们天然不需要；
4. **安全边界更硬**：WebView 白名单 + 进程隔离，优于他们的 token 头门禁；
5. **包体量**：~10MB 壳 + sidecar，远小于 Electron 100MB+。

## 八、分阶段路线图

```
阶段 1（低成本，推荐先做）：桥服务化
  桥插件注册同源 HTTP 路由 + 公开服务契约（桌面状态、重启、日志、设置）
  页面改为走路由（保留 __DSH_DESK__ 双向通道为私有增强）
  收益：第三方插件可复用桌面能力；桥从「后门」变「正门」
  工作量：桥插件重写 + 壳侧 IPC 接口整理（约 1-2 周）

阶段 2（中成本）：桌面能力编排化
  把「重启宿主/开日志/通知镜像」等编排逻辑从壳挪进桥插件宿主半部
  壳新增命令端口（cmdport.rs + executor.rs），退化为「原生执行器」
  收益：桌面能力以插件形态存在，符合「一切皆插件」；壳代码变薄
  工作量：中（涉及 lib.rs 命令重构 + 桥插件扩展）

阶段 3（中成本，可选）：工程成熟度
  启动分档 + 每档失败路由 + 健康 checkpoint + 渲染健康门禁
  收益：崩溃恢复体验质变（对齐甚至超越参考项目）
  工作量：中

阶段 4（低成本，按需）：轻量补丁机制
  sidecar:assemble 加补丁层 + 双断言测试
  只在遇到上游 bug 时启用
  工作量：小
```

## 九、不做清单

- 多 profile + 托盘切换（产品无此需求）；
- 插件市场（生态未到）；
- 三种窗口呈现模式（WebView2 的材质是另一套技术活）；
- 同进程方案（牺牲容错，与 D6 精神一致）。

## 十、验收标准（阶段 1+2 完成后）

1. 第三方插件能通过公开契约（`desktopState`/`desktopCommands`）使用桌面能力，且无需 IPC 后门；
2. 纯浏览器环境（无壳）下桥插件全量退化，Web UI 功能不受影响；
3. `__DSH_DESK__` 私有通道关闭后，设置区全部功能仍可用（走 ② 路由）；
4. sidecar 崩溃时壳能重启宿主，桌面与命令端口不受影响；
5. 现有 profile 初始化、sidecar 分发、安全边界（白名单/凭证）行为不变；
6. 全部现有测试通过（desk-core 45 例 + bridge 退化契约 + 新增 cmdport/路由测试）。
